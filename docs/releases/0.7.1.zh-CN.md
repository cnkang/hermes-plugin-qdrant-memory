# Runtime 0.7.1：保住恢复点，遇到未结回执即停止

Runtime 0.7.1 修复公开 0.7.0 wheel 上的两个升级安全问题。dense 检索、点身份、
已存 payload、embedding fingerprint、授权、确认写入与四个 MCP 工具均不变。

## 中断的升级保留恢复点

在 0.7.0 中，apply 中断后再跑普通 `upgrade plan`，会用新的 `planned` 记录覆盖
已保存状态。备份目录仍在，但 `status` 丢失其路径与步骤历史，还可能返回相同的
`plan_id`，看起来像什么都没执行过。

Runtime 0.7.1 在既有 writer lease 内读取已保存记录。已执行步骤、且尚未到达
`ready` 的 plan 会保留阶段、失败原因、步骤记录与恢复点引用。`upgrade plan`
返回现有 plan 标识，并提示操作者续跑。

若 plan 已过期、无法继续，`upgrade plan --replace` 会先把旧 plan 及其备份引用
归档到 profile 内，再保存新 plan。操作者不必手动删除控制面文件。

`apply` 与 `resume` 取得 lease 后重新读取 plan。若取锁期间另一轮替换了 plan，
旧 plan 被拒绝，新记录不会被覆盖。重复 resume 只报告 `already_applied`，
不会新增备份或策略 generation。

若 embedded 备份已在磁盘上、但步骤记录丢失，`resume` 会重新打开副本、核对计划
点数并沿用该路径。中断的 activate 只有在已提交的策略记录匹配目标、且实际
destination 仍满足 verify 步骤时，才会被报告为完成。

## Shared Owner 回执阻止 plan 与 apply

在 0.7.0 中，已落盘但关联事件尚未到达终态的 Shared Owner 生命周期回执会被普通写入
互锁看到，升级 planner 却看不到。`plan` 可能漏报 blocker，`apply` 可能返回
`ready`。

Runtime 0.7.1 让两个入口复用 `qdrant_memory/shared_state.py` 的只读判定。它覆盖
`owner_events_v1` 中关联事件尚未到达终态的回执，以及未完成的 `shared_requests_v1` 行。
关联事件已处于终态的回执仍视为崩溃残留，不会阻止升级。

`plan` 报出 blocker。`apply` 与 `resume` 在取得 lease 后重新检查，因此 plan 之后
才出现的回执也会被拦截。既有 reset、scope-delete、failed event 与 quarantined
event blocker 保持不变。维护命令不会自动清理回执、重新提取或重放待处理事件。
先完成既有 Owner 恢复流程，原 plan 仍有效则 resume；已过期则使用
`upgrade plan --replace`。

## 兼容性

Runtime 0.7.1 保持 0.7.0 的存储与策略 schema。不包含数据迁移、重新嵌入、索引重建
或默认策略变更。Qdrant Server 1.20.1 仍是推荐的自托管基线，公开的
`qdrant-client` 范围不变。

独立的 `qdrant-memory-mcp` 0.3.4 精确锁定 Runtime 0.7.0，不会自动获得本修复。
后续 MCP 补丁可选择 0.7.1。本 Runtime 发布不改 Hermes Catalog pin，也不请求
上游 Catalog 更新。

## 安装

安装前请检查 [PyPI](https://pypi.org/project/hermes-plugin-qdrant-memory/0.7.1/)
是否已提供该版本：

```sh
python -m pip install 'hermes-plugin-qdrant-memory[mcp]==0.7.1'
```

已有 destination 请保持同一 profile、集合与 embedding pipeline。先跑
`upgrade plan`，审阅 blocker 与索引状态，再在短维护窗口内 apply。失败或中断的
一轮应使用原 plan 标识 resume，默认不会被重新规划。

初始策略升级设计见 [0.7.0 发布说明](0.7.0.zh-CN.md)。
