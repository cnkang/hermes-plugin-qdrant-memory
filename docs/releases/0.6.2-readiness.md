Runtime 0.6.2 carries the receipt-scoped failed-event retry from
[PR #140](https://github.com/cnkang/hermes-plugin-qdrant-memory/pull/140).
The implementation validates the persisted operation plan before it changes
state, requeues only failed operations for the named event and leaves quarantined
events under operator control. Public 0.6.1 does not contain this behavior.

The platform workflow passed on Windows Python 3.11 and 3.14. These checks
pre-date the release metadata change and are not evidence for the final 0.6.2
main SHA.

[Quick Soak run 43136693502](https://github.com/cnkang/hermes-plugin-qdrant-memory/actions/runs/43136693502)
passed on the same base SHA. Its six short x86_64 and ARM64 steady, network and
restart lanes processed 10,256 requests in approximately 492–500 seconds each.
The reviewed reports showed zero unexpected failures, permanent write losses
or duplicates, no `post_writer` error or `ExceptionGroup`, and no failed hard
invariant. The extended six-lane Soak was skipped because this was quick mode.
This is preliminary diagnostic evidence only: the 0.6.2 candidate has a new
versioned main SHA and needs its own short Soak before its full Soak.

The full 0.6.1 Soak passed on the separate 0.6.1 release SHA in
[run 42989965437](https://github.com/cnkang/hermes-plugin-qdrant-memory/actions/runs/42989965437).
It does not include PR #140 and cannot replace the 0.6.2 Soak.

## Outstanding reliability item

[Issue #115](https://github.com/cnkang/hermes-plugin-qdrant-memory/issues/115)
remains open. Two historical Windows Python 3.14 test runs timed out at the
writer-drain boundary before their record-count assertions ran. Those runs did
not establish memory loss, duplication or ledger corruption. Ten later probes
each committed and stored all 100 events, and the full Windows suite passed;
the timeout's exact mechanism is still unknown.

[Issue #118](https://github.com/cnkang/hermes-plugin-qdrant-memory/issues/118)
is now closed after fixing the matrix to build environments with the selected
Python interpreter. The base-SHA Windows Python 3.11 and 3.14 Platform
compatibility jobs both passed. Do not describe #115 as fixed; include its
diagnostic status when reviewing the final Soak and platform logs. Shutdown
continues to retain the writer lease/resources when work has not exited and
emits bounded, redacted writer diagnostics on timeout.

## Required before release

1. Merge this release-preparation PR only after its required checks pass.
2. On the final main SHA, run the short Soak first. Review every lane's logs and
   aggregate before starting the full run. Investigate any writer exception,
   traceback, unexplained rejection, lost write or invariant failure.
3. Run the full six-lane 18,000-second Soak on that same final main SHA. Require
   every expected lane and the final report to pass; no skipped, cancelled or
   incomplete lane counts as success.
4. Pass CI, CodeQL, Platform compatibility, Standalone compatibility and Shared
   destination security for that exact main SHA; run
  `python scripts/check_release_gate.py cnkang/hermes-plugin-qdrant-memory <40-character-SHA>`.
5. Verify Python 3.11 and 3.14 across Linux, macOS and Windows, including the
   Windows writer-drain boundary and standalone compatibility.
6. Build the wheel and sdist from the final main SHA. Check metadata, extras,
   license, SBOM, source inclusion and SHA256. Install the locally built wheel
   in a clean environment and run `pip check`, CLI help, status and verification.
7. Upgrade a disposable profile from public PyPI 0.6.1 to the locally built
   0.6.2 wheel. Verify existing Qdrant records, IDs, scopes, ledger integrity,
   embedding fingerprints and retrieval before and after. Do not migrate or
   reset user collections.
8. Publish only through the existing protected GitHub workflow and PyPI Trusted
   Publishing. Keep the required `pypi` environment reviewer; no local token
   publishing or environment changes.
9. After publication, install `hermes-plugin-qdrant-memory==0.6.2` from public
   PyPI in a separate clean environment and repeat `pip check`, CLI help, status
   and verification. Record the installed version and wheel SHA256.

## Downstream integrations

Runtime 0.6.2 remains compatible with the 0.6.1 Owner event and extraction
interfaces. DSH Native's Owner mode is opt-in and requires Runtime 0.6.1 or
newer; its current adapter does not automatically retry `FAILED` or
`QUARANTINED` events. The published DSH Legacy route remains on its own MCP
and Runtime pins. WorkBuddy's published managed launcher and MCP route also
retain independent exact pins. Publishing Runtime alone must not change either
integration. Update and release downstream pins only after public Runtime
0.6.2 is verified and each integration passes its own release gate.
