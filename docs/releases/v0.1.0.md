# v0.1.0 — limited technical preview

Status: **LIMITED TECHNICAL PREVIEW — `v0.1.0` release record (2026-10-09)**. This
document describes the first release; the `v0.1.0` tag and GitHub Release will be
created from this certification commit when it is published. It supports one writer per destination across all
profiles and hosts, with the documented admission, retention and capacity
limits. It is not a public beta, and these results do not claim broad
production maturity.

## Install

```bash
export HERMES_HOME="/absolute/path/to/your/hermes-profile"
mkdir -p "$HERMES_HOME/plugins"
RELEASE_TAG=v0.1.0   # tag of this release (available after publication)
git clone --branch "$RELEASE_TAG" --depth 1 \
  https://github.com/cnkang/hermes-plugin-qdrant-memory.git \
  "$HERMES_HOME/plugins/qdrant-memory"
ollama pull qwen3-embedding:4b   # default embedding model
hermes memory setup
hermes config set memory.provider qdrant-memory
hermes qdrant-memory init
```

`hermes memory setup` prepares declared dependencies through Hermes PM. See the
[README](../../README.md) for Server/Cloud configuration and the
data-flow/privacy guide.

## Highlights

- Durable native `MemoryProvider`: turn persistence to a private SQLite WAL
  ledger, serialized writes, cached session recall and builtin-memory mirroring.
- Scoped storage (user/agent), exact-ID update/delete, and commit-time delete
  fences that stop stale prepared writes from resurrecting deleted memories.
- Bounded replay and recovery: ledger replay in bounded memory (0–100,000 rows;
  see the [recovery benchmark](../recovery-benchmark.md)), interrupted reset
  recovery, and migration terminal-state accounting
  (`migration_incomplete` / `migration_superseded`).
- Read-only Mem0 migration: JSON and Qdrant sources, dry runs, resumable
  manifests, and exact ID/scope/payload-hash verification.
- Memory inventory and lifecycle: read-only `list` with ledger backlog counts,
  streaming portable `export` (Mem0-importable JSON, re-import with
  `migrate mem0`), and durable `delete-all` — one scope or `--all-agents` —
  with reset-style intent, prepared-write and pending-event invalidation, and
  fail-closed recovery.
- Agent tools `qdrant_memory_search`, `qdrant_memory_add`, `qdrant_memory_update`,
  `qdrant_memory_delete`; maintenance CLI `status`, `init`, `doctor`, `stats`,
  `verify`, `retry`, `list`, `export`, `delete-all`.

## Known limitations

- Writer coordination is local to a profile home; run one writer per
  destination across all profiles and hosts. Server/Cloud multi-writer is not
  supported.
- Turn durability starts when Hermes admits the provider callback; earlier
  host-queue loss is outside the plugin's boundary.
- SQLite ledger history and migration manifests grow on disk; logical scrubbing
  is not physical secure erasure — plan capacity, backups and retention.
- Retrieval is dense-only (no hybrid, rerank, or vector reuse); reported quality
  figures are synthetic regression baselines, not production recall claims.
- Embedded Qdrant permits a single client process: stop the agent before
  maintenance commands.
- Slow local models can exceed the auxiliary-call timeout for memory
  extraction; raise `auxiliary.qdrant_memory_extraction.timeout` and requeue
  timed-out work with `hermes qdrant-memory retry`.
- Inventory and export are CLI-only (`list`, `export`); there is no graphical
  UI for stored memories.
