# Runtime 0.7.3: verify upgrade recovery checkpoints

Runtime 0.7.3 hardens the operator upgrade path. Saved plans are tied to a
profile-local Ledger write watermark, and an embedded recovery point is
published only after its Qdrant snapshot and copied SQLite Ledger pass
verification.

## What changed since 0.7.2

- A plan records the local Ledger write watermark, including committed writes
  and the destination reset epoch. `apply` and `resume` check it again under the
  profile `WriterLease`. A committed local update invalidates the plan even if
  it preserves both the point ID and point count. A destination reset also
  invalidates the old boundary if row IDs later repeat.
- Before publishing an embedded recovery point, Runtime checks the copied
  Qdrant store against the planned point count and embedding fingerprint, then
  validates the copied SQLite Ledger and its saved watermark. Invalid marker
  identities, corrupt Ledger files and mismatched recovery metadata are not
  accepted as recovery points.
- If the profile filesystem runs out of space while the copied Ledger is being
  verified, the operation stops and leaves the recoverable checkpoint available
  for retry with the same plan. Free space and retry; do not replace a valid
  plan just to get past a verification error.
- An unresolved Shared Owner receipt or incomplete shared request continues to
  block the maintenance operation until the existing Owner recovery flow has
  finished.

## Upgrade procedure

Stop every writer that can reach the destination before planning. Run
`qdrant-memory --home /path/to/profile upgrade plan` and review the reported
target, collection, point count and embedding identity. Apply only that saved
plan with `upgrade apply --plan PLAN_ID`.

Use `upgrade status` to inspect a saved plan. It is read-only. Resume an
interrupted plan with its original ID only when the plan is not stale and its
verified recovery point is still available. A local write after planning,
including an update to an existing point, or a completed destination reset
makes the plan stale. Run `upgrade plan --replace` to archive the old plan and
recovery reference and create a new checkpoint at a fresh stopped-writer
boundary. Do not edit or delete the old checkpoint to make it appear reusable.

## Scope, compatibility and recovery limits

The watermark observes committed writes recorded in this profile's local
Ledger. It cannot observe writes made through another Runtime profile, another
host, another credential or a direct Qdrant client. `WriterLease` coordinates
cooperating local writers for the same profile and destination; it is not a
distributed lock. For Qdrant Server and Cloud, isolate all external writers and
take the provider's snapshot at the new boundary before applying an upgrade.

This release does not change dense retrieval defaults, collection identity,
point IDs, payloads, embedding dimensions or embedding fingerprints. Existing
data stays in place. No data migration, re-embedding or index rebuild is
required. The four explicit MCP tools and existing authorization and scope
rules are unchanged. Ordinary MCP operations still do not perform automatic
conversation extraction or expose maintenance commands.

Application rollback means reinstalling a prior Runtime. It does not make an
older Qdrant engine safe for data written by a newer engine. Restoring a
recovery point discards writes made after that point; it is not a substitute
for coordinating external writers or keeping the provider's own backup.

## Compatibility

Runtime 0.7.3 retains Python 3.11+ and MCP Python SDK 1.x and 2.x support. The
Hermes minimum remains the version declared by the native manifests. See the
[validation record](../validation.md) for checks run on this candidate and
environment-dependent checks that remain unverified.

## Installation

Check [PyPI](https://pypi.org/project/hermes-plugin-qdrant-memory/0.7.3/) for
availability, then install into a private environment:

```sh
python -m pip install 'hermes-plugin-qdrant-memory[mcp]==0.7.3'
```

For an existing destination, review `upgrade status` and `upgrade plan` before
applying. Do not use an editable checkout or an unpublished artifact as public
installation evidence.
