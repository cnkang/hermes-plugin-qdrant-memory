# BM25 experiment: final record and reassessment conditions

Recorded on 2026-11-17. Status: **archived on the experimental branch; enablement work is on hold**. Keep PR #152 as a Draft. No merge, release, tag, Runtime/MCP/Skills integration, or upstream repin is part of this record.

## Decision

**Do not enable the tested BM25 hybrid path. Keep dense retrieval as the default.** The independent fixed-configuration experiment is **NO-GO** because the preregistered mixed-query recall benefit did not reproduce. The bounded follow-up executed successfully but remains **EXPLORATORY / INCONCLUSIVE**; no variant added correct recall or surpassed dense ranking quality on development data. Per the stopping rule, do not continue parameter searches solely to obtain a positive result.

This is not evidence that BM25 is universally useless. It is evidence against enabling these configurations for the tested memory scenarios. The dataset is small and dense recall is near its ceiling. A new, independently motivated workload could justify reassessment.

## Dataset and review

The independent corpus contains 172 fictional memories, 132 individually annotated queries and 44 fact groups. Development has 24 queries / 8 groups; holdout has 108 queries / 36 groups. Holdout mixed contains 54 queries / 36 groups, including one no-answer query; its answered subset has 53 queries / 35 groups. Current stale_fact has 30 queries / 30 groups. Tags overlap.

Each query has a query ID, fact-group ID, tags, scope, direct answer IDs, contextual IDs, conflicting IDs and rationale. Current and historical questions use different positives where appropriate. Context is not counted as a direct answer. No-answer queries are retained and reported separately. All questions from one fact group stay on the same side of the development/holdout split.

The user explicitly delegated annotation verification to Codex. Labels are agent-authored and Codex-reviewed, not independently human-reviewed. One development query (`reply-language/q1`) was corrected after the first full CI: the exception record explicitly said Chinese resumes after submission, so both it and the default-preference record are direct evidence. No holdout query or label changed; the final manifest separately hashes the unchanged expanded holdout. Retrieval settings and acceptance boundaries were not tuned against holdout results. See [review](../../independent/REVIEW.md), [annotations](../../independent/annotations.jsonl), [freeze history](../../independent/FREEZE_HISTORY.md) and [manifest](../../independent/freeze.json).

No real Hermes memories, production collections or credentials were used. All Server collections were newly created temporary `bm25_ind_*` collections.

### Current facts, history, unanswered queries and safety

- Old-before-current ordering: 21/30 to 19/30, change -6.67pp, 95% CI [-20.00pp, +6.67pp]. This includes a returned old fact with the current answer missing. It does not establish the preregistered <=2pp regression bound.
- Current-answer presence in top 8: 30/30 for both paths. Presence is not the same as ranking the current fact first.
- Historical accuracy: 16/31 for both paths; delta interval [-12.90pp, +12.90pp]. The requested-time answer must precede conflicting-time evidence; history is not automatically penalized as stale.
- No-answer holdout: 3 queries / 2 groups. Both paths returned distractors for every query; average count 5.67. This is not scope leakage: they are other visible memories. No common dense/RRF score threshold was applied. The ten-group requirement is unmet, so this component is INCONCLUSIVE.
- Fixture lifecycle and raw returned-ID audits passed: add, same-ID text/vector replacement, old sparse token removal, new token visibility, deletion invisibility in both paths, different user/agent/null-agent isolation and repetition after same-container/same-volume restart. These are deterministic fixture checks, separate from real-model semantic evidence.

### Cases worth revisiting

- `task-priority/q3`: correct branch record `d` was dense rank 2 but absent from hybrid top 8. The mixed/code/identifier recall loss reproduced across full CI executions.
- `issue-label/q2`: the question asks for the earlier issue label. Hybrid promoted current `b` ahead of correct historical `a`; newer is not always the requested answer.
- `retry-policy/q1`: in the final CI, dense put current `b` before old `a`, while hybrid put old `a` first. An aggregate stale-fact improvement does not mean there are no individual regressions.
- The local backup-policy and retry-policy regressions did not both reproduce in every CI run. Preserve machine/run distinctions rather than reporting every local failure as a CI failure.

## Bounded follow-up: what was tried

Development only: 24 queries / 8 groups, with 20 answered queries. All variants keep RRF k=60 and 24 candidates per leg. Test native 1:1, 2:1 and 4:1 weights; probe multilingual 2..15, multilingual 1..64 and code 1..64 with fixture vectors. Wider token lengths were then tested with real embeddings because the probe rescued a short token. There was no broad tokenizer/weight/k/b grid search and no new holdout was exposed.

An analytic fixture and [pinned Qdrant source](https://github.com/qdrant/qdrant/blob/v1.20.0/lib/segment/src/common/reciprocal_rank_fusion.rs) show that native weights compress positions: `1 / ((rank + 1) / weight + k - 1)`, with zero-based rank. This differs from multiplying the RRF contribution by a weight. With k=60, rank-zero weight 1 versus 4 contributes 1/60 versus 1/59.25; increasing the dense weight does not remove the strong preference for records present in both lists. This is defined backend behaviour, not a demonstrated Qdrant bug.

Offline scalar-weighted controls were added after the first local development result, explicitly recorded as post-hoc. They use the captured candidates and deterministic ID tie-breaking. Independent leg requests can differ from native prefetch ordering/candidate selection, so their fusion reconstruction residuals are retained. They are not an exact simulation of the backend or a selected production strategy.

### Explaining the apparent ~41 ms retrieval increment

The follow-up records embedding, HTTP/client, decoding, server-reported time and response bytes, using original payloads, minimal payload projection and no-connection-reuse controls. Each mode/path has 72 observations (3x24), below the original >=100 pairs/round confirmation requirement.

| Mode | Dense client p95 ms | Hybrid client p95 ms | Dense server p95 ms | Hybrid server p95 ms |
|---|---:|---:|---:|---:|
| original | 3.11 | 43.98 | 0.60 | 0.83 |
| minimal | 43.97 | 44.11 | 0.67 | 0.84 |
| no_keepalive | 7.16 | 6.95 | 0.62 | 0.98 |
| e2e | 3.52 | 4.32 | 0.69 | 1.07 |

The minimal projection also made dense client time approximately 44 ms, despite sub-millisecond server retrieval. Removing connection reuse reduced both client paths to approximately 7 ms. This supports an HTTP-response/connection-pattern effect outside the measured retrieval operation; attributing the entire increment to BM25 computation is unsupported. Client-minus-server also includes serialization, response handling and other overhead, not only network travel. No packet capture established a specific Nagle/delayed-ACK cause.

No-keepalive control totals include client construction/close overhead; its client_ms column excludes that overhead. Minimal projection retains the original dense24/hybrid8 response cardinalities. Controls were kept alongside original results, not substituted to report only the fastest latency. They do not recommend disabling keepalive in Runtime.

## Limitations

- Fictional, small corpus; near-ceiling dense recall limits measurable recall gains. Results do not establish universal superiority of either retrieval family.
- Only eight development groups; no reliable configuration winner can be selected from that alone. Follow-up scalar controls were explicitly post-hoc.
- Agent-reviewed labels, limited no-answer groups, overlapping strata and broad temporal intervals limit generalization.
- Retrieval evidence is evaluated, not generated final-answer correctness. BM25 does not itself resolve time validity, negation or current-versus-history intent.
- CPU/GPU/provider/platform numerical and ranking/tie differences can affect fine ordering. Raw evidence is per run; cross-machine results were not pooled.
- Startup is not fully process/model-cold. Follow-up latency is diagnostic, not a replacement confirmation benchmark.
- GitHub once failed to allocate three macOS hosted runners before any steps ran. Check annotations identified capacity constraints; targeted retries passed. These were infrastructure failures, separate from BM25 quality and the latest successful experiment runs.

## Reproduce and reassess later

Use a fresh temporary pinned Server, the exact real model digest and fictional data; never a production collection. Follow [independent setup](../../independent/README.md) and [follow-up setup](../../bm25_followup/README.md). Core commands:

```sh
python -m unittest discover -s experiments/independent -p 'test_*.py' -v
python experiments/independent/lifecycle.py --container bm25-independent-local --output /tmp/bm25-record/lifecycle.json
python experiments/independent/run.py --split dev --rounds 1 --latency-pairs 2 --latency-queries 2 --lifecycle-report /tmp/bm25-record/lifecycle.json --output /tmp/bm25-record/dev.json
python experiments/independent/run.py --split holdout --rounds 3 --latency-pairs 100 --lifecycle-report /tmp/bm25-record/lifecycle.json --output /tmp/bm25-record/holdout.json
python experiments/bm25_followup/explore.py --output /tmp/bm25-record/followup.json
```

Prepare the container named in the lifecycle command and set QDRANT_IMAGE_DIGEST as documented. Replaying the old holdout reproduces historical evidence; it does not make the exposed queries unseen again.

Reopen the research only for an independently observed use case where dense misses useful evidence, or a separately justified retrieval change. Before tuning, freeze a new plan, annotation rules, scope/temporal/no-answer boundaries and latency budget. Construct diverse new fact groups with competitive distractors, allocate enough no-answer groups, and split by fact group. Do not retain only scenarios that a preliminary model run happens to make BM25 win. Select candidates on development, then evaluate a fresh untouched holdout.

A future positive result would at most justify a separate Server-only, default-off experimental entry point. This archive authorizes no enablement.
